## Akzeptanzkriterien

1. **Scheduler `GET /api/v1/tapes`**
   - Route registriert in `scheduler/src/api/mod.rs` (öffentlich, **nicht** unter `/internal`).
   - Query-Parameter: `q`, `visibility` (`shared|private`), `owner_caster_id`, `limit`, `offset`, `source` (`live|upload`), `status` (`pending|processing|ready|failed|deleted`), `visible` (`true|false`).
   - Viewer-Scope via `X-Caster-Id`: `WHERE (visibility='shared' OR caster_id=viewer)` — analog `tracks::search`.
   - Sortierung: `created_at DESC, id`. Pagination via `limit`/`offset`.
   - Response: Array von `TapeDto` (neues DTO, Felder siehe `tapes` Tabelle + `slug`).
   - Tests: Sichtbarkeit (fremde private → 404/leer), Filter, Pagination.

2. **Scheduler `POST /api/v1/queues/{id}/activate`**
   - Route registriert in `scheduler/src/api/mod.rs`.
   - Body: `{ "mode": "settings" | "broadcast", "starts_at"?, "ends_at"?, "show_id"?, "title"?, "description"? }`.
   - `mode=settings`: setzt `settings['queue.active_id'] = {id}` (upsert), `204`.
   - `mode=broadcast`: legt einen `kind='playlist'` Broadcast an (`queue_id={id}`, `starts_at` default `now`, `ends_at` optional, `show_id` optional) und startet ihn sofort (`POST /broadcasts/{id}/start` in derselben Transaktion). Response: `201 { broadcast_id }`.
   - Validierung: Queue muss existieren; bei `mode=broadcast` `starts_at <= ends_at` (falls `ends_at` gesetzt).
   - Optimistic Lock via `version` im Body (Pflichtfeld).
   - Tests: beide Modi, Validierung, Versionskonflikt, fehlende Queue.

3. **Portal `TapeApi` (Trait + `HttpTapeApi` + `FakeTapeApi`)**
   - Trait in `portal/src/api_client.rs` (neuer Abschnitt nach `TrackApi`).
   - Methoden: `list(viewer, query) -> Result<Vec<Tape>, TapeError>`, `get(viewer, id) -> Result<Tape, TapeError>`.
   - `HttpTapeApi`: Bearer `SERVICE_TOKEN` + `X-Caster-Id`; Basis-URL `/api/v1/tapes*`.
   - `FakeTapeApi`: In-Memory, enforces gleichen Viewer-Scope wie Scheduler.

## Risiken

- **Viewer-Scope Inkonsistenz**: `tapes.visibility` Default ist nicht `shared` (Schema: `visible INTEGER DEFAULT 0`, aber `visibility` Spalte existiert nicht — `tapes` hat `visible` Flag + `source`). Der Plan nutzt `visible=1` als „öffentlich“ und `caster_id=viewer` als eigene. **Korrektur**: `tapes` Tabelle hat **keine** `visibility` Spalte, nur `visible` (0/1) und `source` (`live|upload`). Der Scope muss angepasst werden: `WHERE (visible=1 OR caster_id=viewer)`. Filter `visibility` Parameter entfällt; stattdessen `source` + `visible` Filter.
- **Queue Activate Transaktion**: `mode=broadcast` erfordert Broadcast-Create + Start in **einer** TX (atomar). `store::broadcasts::create` + `start_broadcast` Logik muss transaktionssicher aufgerufen werden (neue Store-Funktion `create_and_start_playlist_broadcast`).
- **Settings Key Kollision**: `queue.active_id` ist ein einzelner Key — mehrere Queues können nicht gleichzeitig aktiv sein. Das ist beabsichtigt (ein aktiver Queue = „Sendung“).
- **Portal Fake Parität**: `FakeTapeApi` und `FakeQueueApi::activate` müssen exakt denselben Scope/Validierungen erzwingen wie der Scheduler, sonst maskieren Tests Bugs.
- **Migration**: Keine DB-Migration nötig (Schema hat `tapes`, `settings`, `queues`, `broadcasts` bereits).
